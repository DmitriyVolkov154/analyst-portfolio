# Marketplace Order

Учебный проект системного аналитика по проектированию процесса заказа товара на маркетплейсе.

## Цель проекта

Спроектировать основные бизнес-процессы и системное взаимодействие участников при создании, оплате и доставке заказа, включая отказоустойчивость и асинхронную обработку событий.

## Участники

- Customer — покупатель
- Seller — продавец
- Order Service — управление заказом и его состоянием
- Payment Service — обработка и подтверждение платежа
- Delivery Service — организация доставки
- Marketplace — клиентское приложение и бизнес-логика маркетплейса
- Kafka — транспорт для асинхронных событий

## Жизненный цикл заказа

```text
CREATED
   ↓
RESERVED
   ↓
PAID
   ↓
IN_DELIVERY
   ↓
DELIVERED
   ↓
RECEIVED
```

### Значение статусов

- `CREATED` — заказ создан.
- `RESERVED` — товар зарезервирован за заказом.
- `PAID` — Payment Service подтвердил успешную оплату.
- `IN_DELIVERY` — заказ передан в доставку.
- `DELIVERED` — заказ доставлен в пункт выдачи или по адресу.
- `RECEIVED` — покупатель фактически получил заказ.
- `CANCELLED` — заказ отменён с указанием причины.

`DELIVERED` и `RECEIVED` — разные состояния: факт доставки не означает факт получения покупателем.

## Резервирование

После создания заказа товар резервируется на ограниченное время — в рамках проекта используется правило 15 минут от момента создания заказа.

При истечении срока оплаты заказ переводится в `CANCELLED`, товар освобождается для других покупателей.

Заказ не удаляется физически: история операции сохраняется.

## Оплата

Payment Service отвечает за проведение платежа и подтверждение его результата. Order Service является владельцем состояния заказа.

Для защиты от повторной оплаты используется `Idempotency-Key`.

Отсутствие ответа Payment Service не означает, что платеж был не выполнен: запрос может быть обработан, а ответ потерян. Поэтому окончательный результат определяется подтверждением Payment Service или асинхронным событием `PaymentSucceeded`.

После успешной оплаты продавец получает уведомление о необходимости подготовить заказ к отправке.

## Асинхронное взаимодействие

Для передачи результата оплаты используется событийная модель:

```text
Payment Service
       ↓
PaymentSucceeded
       ↓
     Kafka
       ↓
 Order Service
```

Каждое событие содержит уникальный `event_id`.

Order Service проверяет таблицу обработанных событий. Повторная доставка одного события не должна повторно выполнять бизнес-операцию.

Ключевой принцип обработки:

```text
BEGIN TRANSACTION
  UPDATE orders SET status = 'PAID'
  INSERT INTO processed_events(event_id)
COMMIT
```

Изменение статуса заказа и фиксация обработки события выполняются атомарно. Если сервис падает до commit, событие может быть доставлено повторно. Если commit уже выполнен, повторное событие игнорируется.

## Отказоустойчивость

В проекте рассматриваются:

- двойной клик по кнопке оплаты;
- повторный запрос оплаты с тем же `Idempotency-Key`;
- потеря ответа Payment Service;
- временная недоступность Order Service;
- повторная доставка Kafka-события;
- отмена неоплаченного заказа;
- отмена уже оплаченного заказа и возврат денежных средств;
- конкурентная покупка ограниченного количества товара;
- невозможность определить срок доставки;
- отсутствие подходящего пункта выдачи;
- отмена заказа продавцом, например из-за повреждения товара.

## Основные бизнес-правила

Подробные правила находятся в [`requirements/business-rules.md`](requirements/business-rules.md).

Ключевые правила:

- заказ нельзя перевести в `PAID` без подтверждения успешной оплаты;
- повторная обработка одного `event_id` не должна повторять бизнес-эффекты;
- оплаченный заказ при отмене запускает процесс возврата денежных средств;
- статус заказа хранится и изменяется Order Service;
- заказ не удаляется при отмене.

## Модель данных

SQL-схема основных сущностей находится в [`database/schema.sql`](database/schema.sql).

Основные сущности:

- `customer`
- `product`
- `orders`
- `order_item`
- `delivery`
- `payment`
- `processed_events`

Цена товара фиксируется в `order_item` на момент оформления заказа, чтобы дальнейшее изменение цены в каталоге не меняло сумму уже созданного заказа.
